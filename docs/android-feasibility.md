# 安卓版可行性

结论：可以做安卓版，而且可以不改现有桌面功能、不改现有处理结果。做法是新增一个安卓外壳，调用现在的 `watermark-core`。现有的 Windows 安装包、便携 zip 和 Linux 包不能装到安卓上。

这次只做分析，没有改算法、界面、模板或安装包，也没有生成安卓工程。

分析时的代码是 `role/zss` 的 `74ca23f`。桌面版本号仍是 0.1.0。

---

## 1. 不改现有结果是什么意思

安卓版如果要做，必须同时满足下面几条：

- 去水印、修改相机时间仍然可以分开使用。两项的默认、开关和失败时写不写文件，都跟现在的桌面版一致。
- 输入是同一份图片字节、同一组选项时，还原像素、时间文字、报告判定和桌面版一致。
- 像素门禁不降低：合成留出集仍是 MAE ≤ 2、最大差 ≤ 6、夹断像素为 0、PSNR > 50、95% 通过。框外像素保持逐字节一致。
- 不改豆包模板，不改机型那一行，不把 IoU 0.38、NCC 0.48 放宽。原图没有秒时不补秒。
- 不接入 ONNX，不覆盖用户原图，不拷贝内容凭证。
- 桌面界面、命令行和水印公式保持原样。安卓需要的选图、保存和布局另做。

---

## 2. 现有程序分成哪两层

计算在 `crates/watermark-core`。它没有 `target_os` 分支，也没有自己开线程。图片从字节解码，字体用 `include_bytes!` 打进程序。对外就是现有的这些函数：

- `decode_bytes`
- `process_best`
- `detect_camera_time`
- `edit_camera_time`
- `encode_png`

桌面壳是 Tauri 2。窗口命令把图片和模板编成 base64，再交给上面这些函数。`src-tauri/src/lib.rs` 里已经有 `#[cfg_attr(mobile, tauri::mobile_entry_point)]`，这只是 Tauri 模板留下的入口，仓库里没有 `gen/android`，这台机器也没有 Android SDK 或 NDK。

模板在 `resources/doubao`，大约 212 KB、17 个文件。桌面版按可执行文件旁边的目录读取。

`image` 0.25.5 用纯 Rust 的 PNG 和 JPEG 解码器，默认特性会带上 `rayon`。逆运算和水印定位本身是单线程循环，不靠并行把像素加总。

---

## 3. 为什么计算层可以原样共用

安卓外壳只要把用户选中的原始文件字节和同样的 `ProcessOptions` 交进去，走的就是桌面版同一条代码。ARM64 和 x86_64 都是小端。模板 JSON、16-bit alpha、bias PNG 和 Inter 字体子集都是程序里的字节，不靠系统字体。

2026-11-21 11:45（北京时间），用 Rust 1.100.0 把现有 `watermark-core` 测试在两种发布优化下各跑了一遍，没有改测试，也没有改源码：

| 目标 | 结果 |
|---|---|
| `x86_64-unknown-linux-gnu` release | 库测试 22 项通过，集成测试 14 项通过 |
| `aarch64-unknown-linux-gnu` release，`qemu-aarch64-static` | 库测试 22 项通过，用时 28.42 秒；集成测试 14 项通过，用时 5.32 秒 |
| 同一 ARM64 目标的 debug | 同样 22 项和 14 项通过 |

这里面包含现在已经卡住的结果：白线槽上的 `2026.11.05 09:19`、柜门缝不能认成 `07:12`、浅色墙、只改时间、没有时间就不写出原图副本、确认未通过时不去水印、关闭改时间时豆包像素不变、留出集 95% 门禁。

这次跑的是 Linux 上的 ARM64，不是安卓的 bionic，也不是手机或模拟器。核心没有 C 编写的图像库，所以它说明公式、识别和编码在 ARM64 优化后仍然满足现有断言。真正的安卓包还要用 `aarch64-linux-android` 再对一次，对照物仍然是这套测试和桌面输出。

---

## 4. 现有安装包不能直接当安卓版

Windows 程序依赖 Windows 8 以后才有的系统库，界面还依赖 WebView2。这些在安卓上不存在。deb、AppImage 和 `watermark-cli` 的本机 HTTP 服务也不是安卓应用。

安卓版要单独编一个包。界面跑在安卓系统 WebView 里，计算仍然进 `watermark-core`。

---

## 5. 外壳要新做，不能改桌面界面来凑

桌面界面是 1180×780 的窗口，用拖放、目录选择、双画布、滚轮和空格对比。这些如果直接改成手机操作，桌面功能就会变。安卓界面应单独做，或者用只在安卓编译时生效的分支，桌面那条路径保持现在的文件。

安卓外壳要守住的输入输出：

- 从用户选中的文件读出原始字节，再调用 `decode_bytes`。不能先让相册或系统把图重压缩、改尺寸、转成 HEIC 以外的另一种编码。现在的解码器不接受 GIF、动图和 WebP；系统先转码再送进来，结果就不是同一张图。
- 模板使用打进安装包的同一批 `resources/doubao` 字节，校验方式不变。
- 保存到用户指定的新文件或分享出去，不覆盖原图。
- `no_watermark`、`camera_time`、低置信度确认、手动框、默认 PNG 这些选项的含义与 `ProcessOptions` 一致。
- 4K 图的 RGBA 大约几十 MB，base64 还会再占一份。内存不够就明确失败，不能偷偷缩小图片。

命令行可以继续只服务桌面。安卓不必跑 `tiny_http`。

---

## 6. 发版前还要补的对照

ARM64 上现有测试已经通过，但测试没有把每一张桌面输出的 PNG 文件和安卓输出并排保存。实现安卓包时要增加对照，不替换现有测试：

- 同一批图片字节、同一组选项，桌面和安卓解码后的 RGBA 一致，报告里的判定、模板、标志和相机时间一致。
- 去水印打开且不改时间、只改时间、两项都做，三条都要对。
- 需要确认、找不到时间、原图带秒，这几种边界保持现在的写文件规则。

如果安卓目标上出现像素差异，就停下来，不放宽比较，也不为了安卓去改桌面已经通过的公式。

---

## 7. 以后实现时要新增的部分

这些不属于这次提交：

- Rust 目标 `aarch64-linux-android`，以及 Android SDK、NDK。最低系统以 `tauri android init` 生成的 `minSdk` 为准，这次没有生成，所以不写一个未验证的 API 级别。
- 安卓工程、相册读取权限和保存路径。只读用户选中的图，不申请整个存储。
- 手机布局。
- 安装包仍然不放 ONNX。桌面安装包小于 30 MB 的限制继续只约束桌面包。
- 真正打包时再改版本号。这次不改 0.1.0。

实现应放在新的分支上。合入前先跑现有的 `watermark-core` 测试，确认桌面结果没有被带着改掉。
